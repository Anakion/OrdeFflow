# 🧾 Шаг 2. Ack — подтверждение обработки

> **Кафе-сценарий:** бариста расписывается за заказ только когда кофе уже готов и выдан.
> Если бариста упал в середине — заказ возвращается на стойку, другой бариста его заберёт.

---

## 💬 Простыми словами — от чего защищает ack

**Ack защищает от падения Worker'а.**

```
Упал Worker (нет сети, перезагрузка, ошибка в коде)
    → ack не был отправлен
    → RabbitMQ возвращает сообщение в очередь
    → другой Worker или этот же после перезапуска заберёт его  ✅
```

---

## 🎯 Проблема шага 1

На шаге 1 у нас было `no_ack=True`:

```python
async with queue.iterator(no_ack=True) as messages:
```

Это значит: **«RabbitMQ, удали сообщение из очереди в момент, когда отдал его worker'у».**

```
RabbitMQ → отдал заказ #1 → заказ удалён из очереди  ← уже здесь!
                ↓
           worker начал «готовить кофе»
                ↓
           worker упал / Ctrl+C
                ↓
           ❌ Заказ потерян навсегда. Клиент не получит ни кофе, ни письмо.
```

В веб-интерфейсе **Ready = 0**, хотя заказ не обработан — RabbitMQ уже о нём не знает.

---

## ✅ Решение — ручной Ack

Worker сообщает RabbitMQ **«я обработал»** только после того как реально всё сделал:

```
RabbitMQ → отдал заказ #1 → заказ переходит в "Unacked" (не удалён!)
                ↓
           worker начал «готовить кофе»
                ↓
           worker упал / Ctrl+C?
           → nack → заказ возвращается в Ready → другой worker заберёт  ✅
                ↓
           worker справился?
           → ack → RabbitMQ удаляет заказ  ✅
```

В веб-интерфейсе пока идёт обработка: **Ready = 0, Unacked = 1** — заказ под контролем.

---

## 🔑 Ключевые понятия

| Термин | Что означает |
|--------|-------------|
| **Ack** (acknowledge) | Worker говорит: «получил и обработал, можно удалять» |
| **Nack** (negative ack) | Worker говорит: «не смог обработать, верни в очередь» |
| **Unacked** | Сообщение отдано worker'у, но ack ещё не получен |
| **Ready** | Сообщение в очереди, ещё не отдано ни одному worker'у |
| **message.process()** | Контекст-менеджер aio-pika: ack при успехе, nack при ошибке |

---

## 🔍 Главное изменение в коде

### Шаг 1 (без ack):
```python
# Сообщение удаляется в момент получения — опасно!
async with queue.iterator(no_ack=True) as messages:
    async for message in messages:
        order = json.loads(message.body.decode())
        # если упадём здесь — заказ потерян
        await asyncio.sleep(3)
```

### Шаг 2 (с ack):
```python
# Сообщение в Unacked пока не выйдем из блока message.process()
async with queue.iterator() as messages:       # ← no_ack убран
    async for message in messages:
        async with message.process():          # ← ack/nack управляется автоматически
            order = json.loads(message.body.decode())
            # если упадём здесь — nack, заказ вернётся в очередь  ✅
            await asyncio.sleep(3)
        # ← сюда дошли без ошибки → ack отправлен → заказ удалён  ✅
```

### Почему Producer не изменился?
`send_order.py` на шаге 2 **идентичен** шагу 1. Это ключевой момент:
> Producer не знает и не должен знать, как Consumer обрабатывает сообщения.
> Изменения в механизме надёжности — только на стороне Consumer.

## 🧪 Эксперименты

### 🔬 Опыт 1 — Нормальная работа с ack

Запусти `worker.py`. Отправь заказ:

```bash
python3 send_order.py 1
```

В терминале worker'а увидишь:

```
⏳ Начинаю обработку заказа #1...
   (3 секунды тишины — «готовим кофе»)
✅ Письмо отправлено на anna@example.com: заказ #1, товары: Кофе в зёрнах, Фильтры V60
```

В веб-интерфейсе за эти 3 секунды:

```
┌───────────────────────────────────────────┐
│  orders │ Ready: 0 │ Unacked: 1 │ Total: 1 │  ← обрабатывается
└───────────────────────────────────────────┘

после ack:
┌───────────────────────────────────────────┐
│  orders │ Ready: 0 │ Unacked: 0 │ Total: 0 │  ← обработано и удалено
└───────────────────────────────────────────┘
```

---

### 🔬 Опыт 2 — «Падение» worker'а во время обработки

Это главный эксперимент шага. Увидишь разницу между `no_ack=True` и `message.process()`.

**Шаг за шагом:**

```bash
# 1. Отправь заказ (пока worker НЕ запущен)
python3 send_order.py 2
# → веб-интерфейс: Ready=1

# 2. Запусти worker
python3 worker.py
# → увидишь: ⏳ Начинаю обработку заказа #2...

# 3. Пока идут 3 секунды — нажми Ctrl+C
#    (имитируем падение worker'а)
```

**Результат:**

```
Worker остановлен
```

Теперь проверь веб-интерфейс → **Ready = 1** 🎉

Заказ **вернулся** в очередь! RabbitMQ не получил ack, поэтому отдал сообщение обратно.

Запусти worker снова — он заберёт заказ #2 и обработает:

```bash
python3 worker.py
# → ⏳ Начинаю обработку заказа #2...
# → ✅ Письмо отправлено...
```

### 🔬 Опыт 4 — Несколько заказов, worker падает в середине

```bash
# Отправь 4 заказа (worker не запущен)
python3 send_order.py 10
python3 send_order.py 11
python3 send_order.py 12
python3 send_order.py 13

# Запусти worker
python3 worker.py
# → начнёт с заказа #10...

# Нажми Ctrl+C сразу после "⏳ Начинаю обработку заказа #10..."
```

Результат: **Ready = 4** — все 4 заказа в очереди.  
Заказ #10 не был подтверждён → вернулся. Заказы #11–13 не отдавались → тоже на месте.

## 💡 Что мы поняли

| Вопрос | Ответ |
|--------|-------|
| Что такое ack? | Сигнал worker'а: «обработал, можно удалять» |
| Что такое nack? | Сигнал worker'а: «не смог, верни в очередь» |
| Что такое Unacked? | Отдано worker'у, но ack ещё не получен |
| Что делает `message.process()`? | При успехе — ack, при любой ошибке — nack |
| Изменился ли send_order.py? | **Нет.** Producer не знает о механизме ack |
| Когда используют no_ack=True? | Только если потеря сообщений допустима (логи, метрики) |
