# 📎 Доп. материал: requeue и два вида «падения»

> Этот файл отвечает на вопрос который часто возникает на шаге 2:
> «Если мы уже используем ack — зачем ещё нужен `requeue=True`?»

---

## Главная идея ack (повторение)

Без ack (`no_ack=True`) — RabbitMQ удаляет сообщение **в момент отдачи** worker'у.  
С ack — RabbitMQ удаляет сообщение только когда worker **явно подтвердил** обработку.

Это значит: пока ack не получен, сообщение висит в статусе **Unacked** и RabbitMQ за него отвечает.

---

## Два совершенно разных вида «падения»

### 💀 Вид 1 — Настоящий краш

Примеры: `kill -9`, отключение питания, потеря сети, OOM-killer убил процесс.

В этом случае TCP-соединение **обрывается без предупреждения**.  
RabbitMQ не получает ни `ack`, ни `nack` — соединение просто исчезает.

**Что делает RabbitMQ:** видит разорванное соединение → все Unacked сообщения автоматически возвращаются в Ready.

```
Worker убит → TCP оборвался → RabbitMQ: нет ack, нет nack
                            → автоматически: Ready+1  ✅
```

Параметр `requeue` здесь **не играет роли** — nack вообще не был отправлен.

---

### 🛑 Вид 2 — Мягкое завершение (Ctrl+C, обработанное исключение)

Примеры: Ctrl+C, необработанное `ValueError`, `TimeoutError` внутри блока обработки.

В этом случае Python ловит ошибку, `message.process().__aexit__` **успевает выполниться** и явно отправляет `nack` в RabbitMQ.

**Что делает RabbitMQ:** получает явный nack → смотрит на параметр `requeue`.

```
Ctrl+C → asyncio отменяет задачу → message.process().__aexit__ вызван
       → явный nack отправлен в RabbitMQ
       → requeue=False: выбросить сообщение  ❌
       → requeue=True:  вернуть в очередь   ✅
```

---

## Сравнительная таблица

| Ситуация | requeue=False | requeue=True |
|---|---|---|
| Настоящий краш (kill -9, обрыв сети) | Вернётся в Ready ✅ | Вернётся в Ready ✅ |
| Ctrl+C во время обработки | Выброшено ❌ | Вернётся в Ready ✅ |
| Исключение внутри `message.process()` | Выброшено ❌ | Вернётся в Ready ✅ |
| Успешная обработка (ack) | Удалено из очереди ✅ | Удалено из очереди ✅ |

---

## Когда что использовать

### `requeue=True` — наш выбор на шаге 2
Worker упал по техническим причинам (Ctrl+C, сеть, память).
Сообщение **нормальное**, просто не повезло — нужно вернуть в очередь,
другой worker или этот же после перезапуска обработает его нормально.

```python
async with message.process(requeue=True):
    ...  # если упадём — сообщение вернётся
```

### `requeue=False` — тема шага 5 (Dead Letter Queue)
Сообщение **битое**: неверный формат, нет обязательных полей, невалидные данные.
Если вернуть в очередь — worker снова упадёт. Получится бесконечный цикл.
Правильнее отправить такое сообщение в отдельную «мусорную» очередь (DLQ).

```python
async with message.process(requeue=False):
    ...  # если упадём — сообщение выброшено (или уйдёт в DLQ)
```

---

## Главный вывод

> Твоя интуиция верна: **основная защита ack-режима — против настоящих крашей**.
> Она работает автоматически, без `requeue`.
>
> `requeue=True` — дополнительная страховка для мягких ошибок (Ctrl+C, исключения),
> когда `message.process()` успевает отправить явный nack.

На шаге 2 используем `requeue=True` — это правильный выбор для технических ошибок.  
Что делать с битыми сообщениями (`requeue=False` + DLQ) — разберём на шаге 5.
